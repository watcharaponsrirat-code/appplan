# Internal implementation contract

Local Node.js (node:sqlite, no packages) + browser ES modules. All Thai user-facing UI; clearly marked demo data. API JSON uses amounts in integer satang. UI converts baht. No remote integrations enabled.

## Server transport
GET /api/bootstrap -> {user:{id,name,roles}, users:[{id,username,name,roles}], state, csrf, integrations:{sheets:false,phone:false}}
POST /api/login {username,password} -> user + csrf (httpOnly session cookie)
POST /api/logout
All other mutations POST /api/action {action,...payload}, X-CSRF-Token header. Result {state, result}. GET bootstrap provides only authorized objects (teacher own; operational roles all). Server enforces mutation authorization. GET /api/health public. GET /api/export?type=... authenticated CSV export. POST /api/upload {name,type,data(base64),projectId} -> {id,name}; GET /api/files/:id authenticated. Max 5MB safe download attachment. JSON max 8MB.

## Domain module (src/domain.mjs)
Exports DomainError (status,message), mutate(state,user,input), visibleState(state,user), totals(state,projectId), validateProject(data,strict=false). mutate changes state, returns result (entity or {ids}) synchronously, throws on invalid operations. Server wraps SQLite BEGIN IMMEDIATE + load + mutate + persist + COMMIT. Auth user management handled server (action user.save). All domain actions below via mutate. Domain must implement audit, state/version checks, ownership, fixed money, immutable snapshots and per-source budget guard. State read restriction enforced visibleState; operational roles can see all, teacher own, audit filtered. Reference records are unverified demo unless imported manually by administrator.

## Frontend files

### School reference selectors (2026-11-11)

The project editor uses an immediate single-select dropdown for heading 3 and derives heading 4. Headings 6–11 show grouped checkboxes: parent checks reveal children, leaf checks update selections immediately, and unchecking a parent clears its descendants using stored snapshot ancestry as well as the current hierarchy. Each category has one optional text/number filter; filtering cannot create an option or submit the form. Full labels wrap without ellipsis. Expansion and query state are transient; selections use the same API below.

Bootstrap adds `state.schoolReferenceCatalog` read from `public/school-reference-data.json`, separate from editable demo `state.references`. Catalog `{schemaVersion,version,sources:[{file,sha256,pages}],issues,items:[{id,category,code,name,parentId,source:{file,page,locator},strategyId?}]}` contains the complete supplied source lists. Categories: `strategicProject`, `strategy`, `standards`, `obecPolicy`, `onesqa`, `worldClass`, `kpd`, `hongson`.

New project/proposed form data sends `referenceSelections:{category:[{id}]}`. The server ignores client reference labels, versions, sources and hierarchy; validates IDs, category, leaf choice and duplicates; and derives `strategy` only from the chosen strategic project's `strategyId`. `strategicProject` is single-select; other alignment categories allow multiple entries. Result rows store `{id,category,code,name,parentId,path:[{id,code,name}],text,fullText,version,dataVersion,source,snapshotAt,strategyId?}`. `referenceDataVersion` and compatibility text fields are stored too. Unchanged server-side snapshots survive central catalog rename/removal, including on project submission, approval, request proposals and printing.

Existing legacy narratives are preserved in `legacyReferences:{category:[{text,resolvedIds:[]}]}`. Client edits cannot delete or forge this history. Explicit `legacyReferenceResolutions:{category:[selectedId,...]}` confirms matching. Changes to selected IDs invalidate earlier matching until reconfirmed. Submission blocks unresolved old narratives. HTTP project/request save rejects newly typed alignment text without selection IDs; unchanged old text may be preserved. A blank legacy payload can upgrade to empty selectors without losing non-reference fields. Direct `validateProject` without a selector schema remains compatible with historical data tooling.

### Requests before project approval (2026-11-11)

`request.save.projectId` is optional/null for a draft. SQLite migrates existing `requests.project_id` to nullable while preserving bodies and history. Unlinked drafts are visible only to their owner, editable with optimistic versions, and can later link to an owned project. An existing link/type stays immutable. Evidence uploads still require a linked project.

All six types may link to draft/submitted/reviewed/approved/returned projects. Creation stores `original` from the approved snapshot when present, otherwise current project data; `baseApprovedVersionId` can be null. Submission requires an owned linked project and the usual reason/type-specific data, but does not require project approval. Preapproval spend/purchase requests need positive amount/source; procurement still checks available approved funds at confirmation. Creation/submission never alters project, versions, outbox, budget, quarters or commitments.

Request review/approval retains existing roles and return flow. An approved amendment with a non-null base version follows existing snapshot, stale-version and budget-obligation checks. An amendment based on a never-approved version records `amendmentApplied:false` and request approval only; it does not create initial project approval or mutate project data. `unable` still never releases commitments. Procurement confirmation and payment retain idempotency and source budgets.
